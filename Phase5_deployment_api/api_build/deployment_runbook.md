# Deployment Runbook
## Hospital Operations & Revenue Risk Intelligence Platform — Prediction API

This document covers building, running, verifying, and operating the
containerized API. It assumes Docker is installed (`docker --version`
should print a version number before you start).

---

## 1. Directory Structure

```
.
├── Dockerfile
├── requirements.txt
├── deployment_runbook.md          <- this file
├── sample_requests.md             <- example API calls and responses
└── app/
    ├── __init__.py
    ├── main.py                    <- FastAPI app and endpoints
    ├── schemas.py                 <- request/response validation models
    ├── preprocessing.py           <- raw input -> model feature vector
    ├── logging_utils.py           <- prediction logging with feature hashing
    ├── models/                    <- trained model artifacts (see Step 2)
    │   ├── risk_model_xgb.joblib
    │   ├── risk_model_label_encoders.joblib
    │   ├── claim_model_xgb.joblib
    │   ├── claim_model_label_encoders.joblib
    │   └── claim_model_provider_rejection_rate.joblib
    └── logs/                      <- created automatically at first run
```

---

## 2. Before You Build: Place the Model Artifacts

The five `.joblib` files listed above come from running
`02_risk_model.ipynb` and `03_claim_model.ipynb` (Phase 3/4) on Kaggle and
downloading the outputs. Copy all five into `app/models/` before building
the image — the Dockerfile bakes them into the image at build time, so if
a file is missing, the container will fail at **startup**, not silently:

```
RuntimeError: Could not load required model artifact: [Errno 2] No such
file or directory: 'app/models/risk_model_xgb.joblib'. Confirm all
.joblib files are present in /app/app/models.
```

This fail-fast behavior is intentional — it is far easier to debug a
container that refuses to start than one that starts but serves broken
predictions because a model silently failed to load.

---

## 3. Build the Image

From the directory containing the `Dockerfile`:

```bash
docker build -t hospital-api:1.0.0 .
```

**What to expect:**
- First build: 1-3 minutes (downloading and installing dependencies)
- Rebuilds after only changing `app/main.py` or similar: a few seconds,
  because Docker reuses the cached dependency-install layer (see the
  comment in the Dockerfile about layer ordering)
- Image size: roughly 600-900 MB (`python:3.11-slim` base + ML libraries
  like xgboost/scikit-learn/pandas, which are not small)

If the build fails on `pip install`, check your internet connection — this
step needs to reach PyPI.

---

## 4. Run the Container

```bash
docker run -d --name hospital-api -p 8000:7860 hospital-api:1.0.0
```

- `-d` runs it in the background (detached)
- `--name hospital-api` gives it a memorable name for the commands below
- `-p 8000:7860` maps the container's internal port 7860 (required by Hugging Face Spaces compatibility) to your machine's port 8000

**Verify it started correctly:**

```bash
docker ps
```

You should see `hospital-api` listed with status `Up X seconds (health: starting)`,
transitioning to `(healthy)` within about 15-45 seconds (the Dockerfile's
`HEALTHCHECK` start period).

**View logs:**

```bash
docker logs hospital-api
```

You should see:
```
INFO | hospital_api | Loading model artifacts...
INFO | hospital_api | All model artifacts loaded successfully.
INFO:     Application startup complete.
INFO:     Uvicorn running on http://0.0.0.0:7860
```

If you see a `RuntimeError` instead, go back to Step 2 — a model file is
missing or misnamed.

---

## 5. Verify the API is Working

```bash
curl http://localhost:8000/health
```

Expected response:
```json
{"status": "ok", "risk_model_loaded": true, "claim_model_loaded": true}
```

For example prediction requests and their expected responses, see
`sample_requests.md`.

**Interactive documentation:** open `http://localhost:8000/docs` in a
browser for a live, clickable interface to both prediction endpoints,
auto-generated by FastAPI from `app/schemas.py`.

---

## 6. Stopping and Restarting

```bash
docker stop hospital-api      # graceful stop
docker start hospital-api     # restart the same container
docker restart hospital-api   # stop + start in one command
```

To remove the container entirely (e.g. before rebuilding with a new image
version):
```bash
docker rm -f hospital-api
```

---

## 7. Updating to a New Model Version

When Phase 3/4 produces newly retrained models:

1. Replace the `.joblib` files in `app/models/` with the new versions
2. Update `MODEL_VERSION` in `app/main.py` (currently `"xgboost-v1-phase3"`)
   so logged predictions are traceable to the model version that produced
   them — this matters for the drift analysis in Phase 6
3. Rebuild and redeploy:
   ```bash
   docker build -t hospital-api:1.1.0 .
   docker stop hospital-api && docker rm hospital-api
   docker run -d --name hospital-api -p 8000:7860 hospital-api:1.1.0
   ```

**Do not** just overwrite files inside a running container — model
artifacts are baked into the image at build time by design (`COPY app/`
in the Dockerfile), so changes to the host filesystem after the image is
built have no effect on a running container.

---

## 8. Known Limitations to Communicate to Anyone Operating This Service

Both models have limited predictive power (see `risk_model_card.md` and
`claim_model_card.md` for full detail):
- **Risk model:** Macro AUROC ≈ 0.53 (barely above random); never predicts
  "High" risk at the default threshold
- **Claim model:** Rejected-class AUROC ≈ 0.65 (modest); flags some but
  not most claims that will actually be rejected

Both `/predict/risk` and `/predict/claim` responses include a `warning`
field stating this directly. **Do not remove or suppress this field** —
it is the load-bearing safeguard against this API being trusted as more
reliable than it has been shown to be.

## 10. Deploying to Hugging Face Spaces (Public URL, No Local Docker Needed to Run It)

This is an alternative to Steps 3-9 above — instead of running the
container on your own machine, Hugging Face builds and hosts it for you,
giving you a public URL anyone can reach.

**One-time account setup:**
1. Go to `huggingface.co/join` and create a free account
2. Go to `huggingface.co/new-space`
3. Choose a name (e.g. `hospital-risk-claim-api`)
4. **SDK: select "Docker"** (not Gradio/Streamlit — those are for different app types)
5. Visibility: **Public** (gives you a URL anyone can access — there is no
   authentication on the endpoints, so do not put real patient data through
   this public instance)
6. Click "Create Space"

**Uploading the project:**

You can either drag-and-drop files through the Space's web UI ("Add file"
button on the Files tab), or use git:

```bash
git clone https://huggingface.co/spaces/<your-username>/<your-space-name>
cd <your-space-name>
# Copy in: Dockerfile, requirements.txt, README.md, app/ (including app/models/)
git add .
git commit -m "Initial deployment"
git push
```

**What happens next:**
- Hugging Face automatically detects the push, builds the Docker image
  using this exact `Dockerfile`, and starts the container
- Build time: typically 2-5 minutes for an image this size (watch progress
  on the Space's "Logs" tab in the browser)
- Once running, your API is live at:
  ```
  https://<your-username>-<your-space-name>.hf.space
  ```

**Verify it's live:**
```bash
curl https://<your-username>-<your-space-name>.hf.space/health
```

Interactive docs: `https://<your-username>-<your-space-name>.hf.space/docs`

**Key difference from local Docker:** Hugging Face Spaces always routes
external traffic to **port 7860** specifically — this is why the
Dockerfile in this repo is configured for 7860, not 8000. If you also run
this locally with plain `docker run`, just map host port 8000 (or any
port you like) to container port 7860:
```bash
docker run -d --name hospital-api -p 8000:7860 hospital-api:1.0.0
```

**If the build fails on Hugging Face:** check the "Logs" tab on your
Space's page — it shows the exact same `docker build` and container
startup output you'd see locally, including the `RuntimeError` from
Step 2 above if a model file is missing.



This Dockerfile runs a single `uvicorn` worker process, suitable for
development, demonstration, and low-traffic use. For production-level
concurrent load:
- Run multiple replicas behind a load balancer (Docker Swarm, Kubernetes,
  or a managed container service), rather than increasing worker count
  inside a single container — this keeps model-loading memory overhead
  predictable per-replica
- Each replica loads its own copy of both models into memory at startup
  (roughly 1-2 GB RAM per replica is a safe planning estimate for these
  model sizes)

This level of scaling is out of scope for the current capstone phase but
is noted here for completeness, per the brief's request for a "deployment
and scaling strategy" (covered more fully in the Final Phase business
presentation).
